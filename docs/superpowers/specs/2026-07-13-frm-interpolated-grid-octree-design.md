# FRM interpolated-grid octree — design

**Status:** implemented July 2026 — `scripts/matlab/frm_grid_*.m` and migrations
`20260713000094_frm_grid_octree.sql` and `20260722000098_grid_pregen.sql`.

## Motivation

The FRM "Full-res" view builds a Potree octree from the **raw measured spiral** of force
samples. At the zoom levels the user needs (deep into small, few-mm regions) the map looks
**sparse** — you see the discrete spiral arms with gaps between them, and aliasing.

In the manual MATLAB workflow the fix is to **interpolate the scattered spiral points onto a
regular rectangular grid**, producing a dense, anti-aliased, filled map. This design brings
that server-side, generated by the crawler, GPU-accelerated where possible, configurable in
density, displayed in `d1-force-dashboard`, and reusing the existing octree pipeline so the
new surface area is small.

It also surfaces the relevant gridding + octree knobs in the Force Crawler settings page.

## Goals

- Server-side (MATLAB/crawler) interpolation of the spiral onto a fine N×N grid.
- Two interpolation methods, selectable: **`splat`** (Gaussian/Shepard, GPU-friendly,
  anti-aliasing) and **`natural`** (Delaunay natural-neighbour, matches the manual workflow).
- Reuse the existing octree pipeline: interpolated grid cells become points fed to
  PotreeConverter and streamed by the existing `FrmOctree` LOD viewer.
- A per-op **fidelity estimate** (hold-out-arms cross-validation) telling the user how close
  the interpolated map is to the measured data, shown in the dashboard.
- Configurable **grid density** (up to 8192) and the octree tuning knobs, in the crawler page.
- "Filled" rendering so the grid octree reads as a continuous surface, not dots.

## Non-goals / deferred

- **Raster image tile pyramid** (DeepZoom/slippy-map) — rejected in favour of reusing the
  octree; revisit only if point-fill proves insufficient.
- **Per-cell confidence/support overlay** (distance-to-nearest-sample as an uncertainty
  channel) — deferred; the single fidelity number answers "should I trust this" for v1.
- **Per-axis fidelity** (separate Fx/Fy/Fz numbers) — deferred; v1 reports one combined figure.
- GPU-accelerating the rest of MATLAB processing — out of scope; only the interpolation.

## Architecture / data flow

```
process_force.m  (new grid_out branch, early-return like octree_out)
    spiral (x,y,Fx,Fy,Fz)
      --interp(method, N)-->  in-disc grid cells (x,y,Fx,Fy,Fz)  + fidelity, arm_ratio
      --> D1GR binary

force_orchestrator.py  (new grid-octree handler; near-clone of process_octree_row)
    D1GR binary --> laspy LAS (force as int16 extra dims) --> PotreeConverter
      --> infra/octrees/grid/<op_id>/  --> DB grid_octree_* + grid_fidelity + grid_arm_ratio

FrmOctree (dashboard)
    Gridded + Full-res -> load grid octree (fill-sized points)
    Full-res (un-gridded) -> raw-spiral octree  (unchanged)
```

The raw-spiral octree, the Live cloud, and the FRM PNGs are **unchanged**. The grid octree is
a **second octree variant per op**, built on demand.

## Component 1 — MATLAB interpolation (`grid_out` branch)

New early-return branch in [process_force.m](../../../scripts/matlab/process_force.m),
alongside the existing `octree_out` branch (~line 207). Triggered by
`opts.grid_out` (output path) plus `opts.grid` struct:

```
opts.grid = struct('n', 2048, 'method', 'splat', ...
                   'cv_fraction', 0.10, 'cv_arm_step', 10)
```

Inputs already computed upstream: `xx, yy` (cartesian spiral), `axes_cut{1..3}` (Fx/Fy/Fz),
`theta` (for arm identification), `stem`.

Steps:
1. **Grid:** equal-aspect bounding box of the spiral; regular N×N grid; `cell = span/N`.
2. **Interpolate each axis** onto the grid:
   - **`splat`:** accumulate each point's force and a unit weight into cells within ~2σ using
     a Gaussian kernel (σ ≈ 0.7·cell), as separable convolutions. `value = sum ./ wsum`.
     Keep cells with `wsum > eps` (a data-support mask). Runs on `gpuArray` when
     `gpuDeviceCount > 0`, else a vectorised CPU path with identical output.
   - **`natural`:** `F = scatteredInterpolant(x, y, v, 'natural', 'none')`; query the grid;
     keep `~isnan` (inside the convex hull). CPU only.
3. **Mask** to kept cells (in-disc / supported); emit those as points `(x, y, Fx, Fy, Fz)` —
   the same 5-float layout as `octree_out`.
4. **Fidelity** (see Component 3), computed before emit.
5. **Write** the `D1GR` binary (Component 4).

Both methods produce the same on-disk artefact; only cell values differ.

## Component 2 — grid-octree handler (orchestrator)

New handler in [force_orchestrator.py](../../../scripts/force_orchestrator.py), a near-clone of
`process_octree_row` (~line 457):

- `claim_grid(...)` / `handle_grids(...)` mirroring `claim_octree` / `handle_octrees`, keyed on
  `grid_octree_status='pending'`.
- `process_grid_row(...)`: run MATLAB with `grid_out` + the `grid` opts (from
  `force_crawler_state`) → read `D1GR` binary via a shared reader → laspy LAS → PotreeConverter
  → publish to `OCTREE_DIR/grid/<op_id>/` → set `grid_octree_status='done'`, `grid_octree_path`,
  `grid_octree_points`, `grid_fidelity`, `grid_arm_ratio`; reuse `_patch_octree_climits` (1/99).
- `_read_octree_bin` generalised to accept both magics (`D1OC`, `D1GR`) and, for `D1GR`, the
  two extra header floats.
- Wired into `run_queue` and the daemon loop next to `handle_octrees`/`handle_renders`.

**Storage precision:** force written as **int16-scaled** LAS extra dims (`scale`/`offset` set
from the per-axis range). Force is 12-bit at source, so int16 is lossless; this roughly halves
attribute storage for the large (up to ~42M-point) grid octrees. `FrmOctree` normalises colour
by the attribute min/max (units cancel); the colorbar converts back to Newtons via the stored
scale so it still reads in N.

## Component 3 — fidelity estimate (hold-out-arms cross-validation)

Computed in MATLAB during `grid_out`, before emit:

1. Identify spiral **arms** by revolution index `floor(theta_cumulative / 2π)` (θ is already
   cumulative pre-wrap in the FRM math).
2. Hold out every `cv_arm_step`-th arm (~`cv_fraction` of the data) as a test set.
3. Re-interpolate with the **same method** on the remaining arms, evaluating the prediction
   **only at the held-out points** (cheap — no full re-grid).
4. Compute, over the **resultant force magnitude** `|F| = sqrt(Fx²+Fy²+Fz²)` (one combined
   number for v1; per-axis is the deferred extension):
   - **nRMSE** = RMSE ÷ (prctile(|F|,99) − prctile(|F|,1))
   - **R²** against the held-out true values
   - collapse to one **`grid_fidelity` = clamp(1 − nRMSE, 0, 1)** reported as a %.
5. **`grid_arm_ratio`** = median arm spacing ÷ cell size — a "are you resolving real structure
   or interpolating across wide gaps" context number.

Both floats travel in the `D1GR` header → orchestrator → DB. Rationale: with a spiral the
error that matters is *across* arms (the invented region), which hold-out-arms measures
directly; random-point holdout would only test the dense along-track direction and flatter the
result. Fidelity honestly degrades when density is pushed past what the arm spacing supports.

## Component 4 — `D1GR` binary format

Little-endian:

| field       | type       | notes                                   |
|-------------|------------|-----------------------------------------|
| magic       | uint32     | `0x44314752` (`'D1GR'`)                  |
| N           | uint32     | number of kept grid cells               |
| fidelity    | float32    | 0..1 (Component 3)                       |
| arm_ratio   | float32    | median arm spacing ÷ cell size          |
| x[N]        | float32    | cell centre x (mm)                       |
| y[N]        | float32    | cell centre y (mm)                       |
| Fx[N]       | float32    | interpolated Fx (N)                      |
| Fy[N]       | float32    | interpolated Fy (N)                      |
| Fz[N]       | float32    | interpolated Fz (N)                      |

(Same body as `D1OC`; adds a 2-float header. The shared reader branches on the magic.)

## Component 5 — "filled" rendering in FrmOctree

A regular grid rendered as fixed-pixel points still looks dotty. For the **grid** octree only,
`FrmOctree` sizes points in **world units ≈ cell spacing**: `gl_PointSize` derived from the
projected cell size (cell_mm × pixels-per-mm), clamped to a sane [1, ~24]px range, so cells
tile into a continuous filled surface at every zoom and LOD level. The raw octree keeps its
current fixed-pixel points. A `fill` (bool) + `cellSize` (mm) prop selects the mode; cellSize
comes from `sqrt(disc_area / grid_points)` or is carried in metadata.

## Component 6 — dashboard UX

- Rename the existing **"Grid binning"** checkbox (ForceDashboard.vue line ~904) → **"Gridded"**,
  mode-aware:
  - **Live + Gridded** → today's client-side `gridCloud` binning (unchanged; still uses `gridN`).
  - **Full-res + Gridded** → the interpolated-grid octree. If not built, request it
    (`grid_octree_status='pending'`) and poll — the same pattern as `buildOctree()`.
  - **Full-res, un-gridded** → the raw-spiral octree (unchanged).
- `FrmOctree` receives `octree-path` = `grid_octree_path` (fill mode) or `octree_path` (raw).
- **Fidelity chip** in the FRM header next to the resolution readout, shown when the grid
  octree is active: e.g. `grid · fidelity ~97% · 1536²`, coloured green/amber past a threshold
  (e.g. ≥95% green). Tooltip includes the arm/cell ratio.

## Component 7 — schema + settings

New migration under [db/migrations](../../../db/migrations):

- `machining_force_analysis`:
  `grid_octree_status`, `grid_octree_path`, `grid_octree_points`, `grid_octree_error`
  (mirror the `octree_*` columns), plus `grid_fidelity` (real), `grid_arm_ratio` (real).
- `force_crawler_state`:
  - `grid_density` int, default **2048**, max **8192**
  - `grid_method` text, `splat` | `natural`, default `splat`
  - `octree_threshold` int (auto-route to octree above this point count). Today the dashboard
    reads `live_cache_points` for this; the new column **decouples** it. Seed its initial value
    from the current `live_cache_points` so behaviour is unchanged until an admin edits it; the
    dashboard's auto-route reads `octree_threshold` once present.
  - `octree_min_node_px` real, default **1** (the LOD streaming detail; currently hardcoded)
  - `octree_budget_cap` int, default **25_000_000** (currently hardcoded)

Directus field registration follows the existing `force_crawler_state` pattern
(`scripts/configure_directus.sql` / the settings interface).

**Crawler settings page** ([Crawler.vue](../../../core/extensions/d1-force-crawler/src/Crawler.vue)):
a new **"Gridding & octree"** form block exposing `grid_density`, `grid_method`,
`octree_threshold`, `octree_min_node_px`, `octree_budget_cap`, each with a short note, saved via
the existing `draft`/`saveSettings` mechanism.

Dashboard reads `octree_threshold` (auto-route), `octree_min_node_px` + `octree_budget_cap`
(passed to `FrmOctree`), and `grid_density`/`grid_method` inform the on-demand grid build.

## Build timing

**On demand.** The grid octree is built when the user first enables **Gridded** in Full-res for
an op (patch `grid_octree_status='pending'`, poll, show), mirroring today's `buildOctree`. This
avoids doubling every crawl's build cost; users opt in per op. (A future crawler toggle to
pre-build grid octrees during the crawl is a possible follow-up, not v1.)

## Error handling

- MATLAB interp failure / empty mask → `grid_octree_status='error'`, `grid_octree_error` set;
  dashboard shows the message (existing `octreeMsg` pattern, gated to not cover the live cloud).
- No GPU → `splat` transparently uses the CPU path.
- `natural` on degenerate/collinear data → caught, surfaced as an error.
- Fidelity uncomputable (too few arms) → store null; chip shows `fidelity n/a`.
- Caddy already serves `/octrees/*` with `Cache-Control: no-cache`; `grid/<op>` inherits it.

## Testing

- **MATLAB:** `grid_out` on a sample .mat with both methods → non-empty masked grid, sane
  bounds, fidelity in [0,1], arm_ratio > 0; CPU/GPU splat paths agree within tolerance.
- **Orchestrator:** `process_grid_row` on a small op → grid octree published, DB fields +
  fidelity set, metadata climits patched, int16 extra dims round-trip.
- **Playwright:** toggle **Gridded** in Full-res → grid octree loads, fills (no visible dot
  gaps at moderate zoom), fidelity chip renders; settings round-trip (save → reload → persisted).
- Reuse the headless swiftshader harness already used for the octree tests.

## Open defaults (baked in; changeable at spec review)

- `grid_density` default 2048, cap 8192.
- `grid_method` default `splat`.
- `cv_fraction` 0.10, `cv_arm_step` 10.
- int16 grid-force storage (vs float32) — recommended given the 8192 ceiling.
- Fidelity chip green threshold ≥ 95%.
